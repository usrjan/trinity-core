# База данных Trinity

## Что это за документ

Это не справочник по таблицам и не список полей. Это описание того, как устроена память дома, почему в ней три таблицы, а не пятнадцать, и как эти три таблицы держат всё остальное. Если `DEPLOY.md` отвечает на вопрос «где что лежит», `ARCHITECTURE.md` — на вопрос «почему это лежит именно так», `CONFIG.md` — на вопрос «откуда дом узнаёт, как себя вести», `SECURITY.md` — на вопрос «что стоит на страже», а `PLUGINS.md` — на вопрос «как добавить дому новую руку», то этот файл отвечает на вопрос «как дом помнит всё, что с ним случилось».

Читать его стоит не как справочник, а как объяснение. Каждый раздел — это ответ на вопрос, который возникает у того, кто смотрит в базу и хочет понять, почему данные лежат именно так, а не иначе.

---

## 1. Почему три таблицы

В Trinity три таблицы: `neuron`, `synapse` и `text`. Не пятнадцать, не сто, а три. Это не «упрощение ради упрощения», а решение, которое родилось после сложности, а не до неё.

Смысл в том, что всё в доме — это сущность, связь или слово. Пользователь — это сущность. Страница — это сущность. Маршрут — это сущность. Настройка — это сущность. Роль пользователя — это связь. Вхождение страницы в раздел — это связь. Название страницы на русском — это слово. Описание страницы на английском — это слово.

Когда всё сведено к трём вещам, дом перестаёт плодить таблицы, которые отличаются только названием. Вместо «таблицы страниц» и «таблицы пользователей» есть одна таблица нейронов, и каждый нейрон знает, кто он, через поле `type`. Это позволяет описывать новые сущности, не меняя схему, и это важно, потому что дом растёт.

## 2. `neuron` — сущность

`neuron` — это таблица сущностей. Здесь живёт всё, что имеет имя: пользователи, страницы, меню, маршруты, настройки, файлы, проекты. Каждая строка — это нейрон, и каждый нейрон знает, кто он, через поле `type`.

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | INT | Первичный ключ |
| `pid` | INT | Родительский нейрон |
| `type` | ENUM | `tree`, `item`, `file`, `user`, `config`, `route`, `template`, `command`, `project`, `construction`, `detail` |
| `tree` | INT | Привязка к дереву |
| `text` | INT | Ссылка на `text.key` |
| `data` | JSON | Все данные нейрона |
| `date` | DATETIME | Дата создания |
| `slug` | VARCHAR | Из `data.slug` |
| `route` | VARCHAR | Из `data.route` |
| `login` | VARCHAR | Из `data.login` |
| `email` | VARCHAR | Из `data.email` |
| `sort` | INT | Из `data.sort` |
| `is_deleted` | TINYINT | Из `data.deleted_at` |
| `hash` | VARCHAR | `SHA2(pid + type + data)` |

**`type`** — это то, что делает нейрон тем, кем он является. `tree` — это раздел, `item` — это элемент, `file` — это файл, `user` — это пользователь, `config` — это настройка, `route` — это маршрут. Один и тот же нейрон может быть разным, и это позволяет описывать дом единообразно.

**`data`** — это JSON, в котором живут все данные нейрона. Здесь `slug`, `route`, `login`, `email`, `password_hash`, `sort`, `deleted_at` и всё остальное, что нужно нейрону. JSON выбран потому, что он гибкий: можно добавить новое поле, не меняя схему, и это важно, потому что дом растёт.

**Генерируемые поля** — это поля, которые MySQL вычисляет сам из `data`. `slug`, `route`, `login`, `email`, `sort`, `is_deleted` и `hash` — это не «дубли», а индексы, которые позволяют искать по данным, не разбирая JSON. Это важно, потому что JSON-поиск медленнее, чем поиск по индексу.

**`hash`** — это `SHA2(pid + type + data)`, и он нужен для быстрой проверки дубликатов. Если хеш совпадает, то нейрон, скорее всего, дубликат, и это позволяет не создавать лишние строки. Хеш виртуальный, потому что он не хранится на диске, а вычисляется при чтении, и это экономит место.

## 3. `synapse` — связь

`synapse` — это таблица связей. Здесь живут отношения между нейронами: роль пользователя, вхождение страницы в раздел, отношение файла к элементу. Каждая строка — это связь, и каждая связь знает, кто родитель, кто ребёнок и как они связаны.

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | INT | Первичный ключ |
| `tree` | INT | Привязка к дереву |
| `parent` | INT | Родительский нейрон |
| `child` | INT | Дочерний нейрон |
| `text_key` | INT | Ключ текста |
| `text_id` | INT | ID текста |
| `data` | JSON | Данные связи |
| `time` | DATETIME | Время |
| `relation_type` | VARCHAR | Из `data.relation` |
| `hash` | VARCHAR | `SHA2(parent + child + data)` |

**`relation_type`** — это то, что делает связь тем, чем она является. `has_role` — это роль пользователя, `member_of` — это вхождение в группу, `has_work` — это отношение работы к организации. Один и тот же родитель и ребёнок могут быть связаны по-разному, и это позволяет описывать отношения гибко.

**`data`** — это JSON, в котором живут данные связи. Здесь `relation`, `granted_by`, `deleted_at` и всё остальное, что нужно связи. Это позволяет описывать не только «что с чем связано», но и «как именно».

**`hash`** — это `SHA2(parent + child + data)`, и он нужен для быстрой проверки дубликатов. Если хеш совпадает, то связь, скорее всего, дубликат, и это позволяет не создавать лишние строки.

---

## 4. `text` — слово

`text` — это таблица слов. Здесь живут названия и описания на разных языках, и каждое слово связано с нейроном через `key`. Один нейрон может иметь несколько языков, и это позволяет дому говорить с гостем на его языке.

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | INT | Первичный ключ |
| `key` | INT | Общий ключ для переводов |
| `group` | INT | Группа |
| `lang` | ENUM | `ru`, `en` |
| `name` | VARCHAR | Название |
| `text` | TEXT | Содержимое |
| `is_active` | TINYINT | Активен ли |

**`key`** — это то, что связывает переводы. Если у нейрона есть `text = 5`, то все строки с `key = 5` — это его переводы, и каждая строка знает свой язык через `lang`. Это позволяет одному нейрону иметь несколько языков, не дублируя нейрон.

**`name`** и **`text`** — это название и содержимое. `name` — это короткое название, которое показывается в меню и заголовках. `text` — это полное содержимое, которое показывается на странице. Оба поля могут быть `NULL`, и это нормально, потому что у некоторых нейронов есть только название, а у некоторых — только содержимое.

**`is_active`** — это флаг, который позволяет «выключить» перевод, не удаляя его. Это полезно, когда перевод устарел, но может понадобиться позже. Если `is_active = 0`, то перевод не показывается, но остаётся в базе.

## 5. Соглашения

Соглашения — это не «правила ради правил», а способ держать базу узнаваемой. Когда открываешь новую таблицу, ты уже знаешь, как искать данные, потому что соглашения одни на всех.

**Мягкое удаление.** Вместо `DELETE` дом ставит `data.deleted_at`, и `is_deleted` становится `1`. Это позволяет «восстановить» нейрон, вернув `deleted_at` в `NULL`, и это важно, потому что удаление — это не «конец», а «пауза».

**Сортировка.** `data.sort` определяет порядок, и шаг — 100. Это позволяет вставлять новые элементы между существующими, не пересчитывая все сортировки. Если нужно вставить элемент между 100 и 200, он получает 150, и это работает.

**Маршруты.** Маршруты живут в нейронах `type='route'`, и они сортируются по `sort`. Порядок важен, потому что специфичные маршруты должны идти до общих, иначе общий перехватит специфичный.

**Конфиги.** Конфиги живут в нейронах `type='config'`, и ключ хранится в `data.key`, а значение — в `data.value`. Это позволяет читать все конфиги одним запросом и не делать `SELECT` на каждый `getConfig()`.

**Пользователи.** Пользователи живут в нейронах `type='user'`, и логин хранится в `data.login`, а пароль — в `data.password_hash`. Пароль хешируется через `bcrypt`, и хеш никогда не передаётся в шаблоны и не попадает в логи.

## 6. Функционал базы на данный момент

Ниже — то, что база умеет сейчас. Это не «список планов», а описание того, что уже работает.

### Нейроны

Нейроны хранят всё, что имеет имя. Они умеют быть деревом, элементом, файлом, пользователем, настройкой, маршрутом. Они умеют иметь родителя через `pid` и привязку к дереву через `tree`. Они умеют иметь текст через `text` и данные через `data`.

Нейроны умеют быть мягко удалёнными через `data.deleted_at`, и это позволяет «восстановить» их, вернув `deleted_at` в `NULL`. Они умеют иметь хеш для быстрой проверки дубликатов, и это позволяет не создавать лишние строки.

### Синапсы

Синапсы хранят связи между нейронами. Они умеют быть ролью, вхождением, отношением. Они умеют иметь данные через `data` и время через `time`. Они умеют быть мягко удалёнными через `data.deleted_at`, и это позволяет «восстановить» их, вернув `deleted_at` в `NULL`.

Синапсы умеют иметь хеш для быстрой проверки дубликатов, и это позволяет не создавать лишние строки. Они умеют иметь `relation_type`, и это позволяет описывать разные типы связей между одними и теми же нейронами.

### Тексты

Тексты хранят названия и описания на разных языках. Они умеют быть связанными с нейроном через `key`, и это позволяет одному нейрону иметь несколько языков. Они умеют быть активными и неактивными через `is_active`, и это позволяет «выключить» перевод, не удаляя его.

Тексты умеют быть сгруппированными через `group`, и это позволяет объединять тексты, которые относятся к одной теме. Они умеют иметь полное содержимое через `text`, и это позволяет показывать на странице не только название, но и описание.

## 7. Что важно помнить, когда меняешь базу

Если ты меняешь базу, помни три вещи. Первое — не добавляй таблицы, если можно добавить нейрон. Три таблицы — это не «ограничение», а решение, и если добавлять таблицы, то дом перестанет быть домом и станет набором таблиц. Второе — не удаляй строки, если можно поставить `data.deleted_at`. Мягкое удаление позволяет «восстановить» данные, и это важно, потому что удаление — это не «конец», а «пауза». Третье — не забывай про индексы. Индексы — это то, что делает базу быстрой, и если их нет, то база становится медленной, и дом начинает ждать.

И ещё одно. База — это память дома, и если память потерялась, то дом потерял себя. Поэтому если что-то идёт не так, сначала посмотри в лог, потом в базу, и только потом — в зеркало.
